# FCOS rapid release

The ordinary path has three jobs: **quality → stage-and-smoke → go-live**. The last job uses the existing protected `fcos-production-release` environment as its single exact decision. A successful build or staging run is never Production authorization.

## Source and build

Start a clean isolated worktree from the freshly read live Vercel deployment commit, not the unfinished main checkout. Copy the current controls with the canonical `.codex/setup.mjs`. Preserve pending features, dirty Apex and untracked migrations. The manifest pins application source/lock hashes and an independently pinned trusted controller commit. Controller changes require their own hosted qualification and handover; ordinary releases keep that controller stable. Before any provider credential is provided, the dispatcher checks the complete hash-bound native handover plan and verifies identical workflow blobs at its current commit and the frozen controller. Ordinary `main` application/documentation commits do not force controller requalification; workflow changes do.

Collect fresh native baseline evidence with `npm run release -- baseline --output /private/baseline.json` using the pinned TLS database read and Vercel identity. The non-secret JSON contains `deploymentId`, `sha`, `configurationDigest`, and `schemaDigest`, collected by the trusted native compatibility reader. Supply only approved public build settings.

The database transport accepts the canonical direct endpoint or the exact FCOS session-pooler host/username pair in `config/fcosConnections.js`, both on port 5432 with certificate and hostname verification. Use the session route where direct IPv6 connectivity is unavailable. Transaction pooling on port 6543 and other project usernames are rejected. Legacy administrator password connections must prove native `session_user`, `current_user` and database identity as `postgres`, with the required transaction mode. Obtain the public CA from the verified project's Database Settings; never reset the database password merely to configure this workflow.

When the database password is unavailable, initial setup and the protected handover may use the existing approved Supabase Management credential (`FCOS_RAPID_SUPABASE_ACCESS_TOKEN`) instead of an administrator database URL. Before issuing temporary access, the frozen controller verifies the pinned project and existing platform-managed role, acquires native atomic ownership, records durable non-secret intent, and submits once. It then verifies the actual TLS socket, native `cli_login_postgres` login, effective `postgres` role, exact platform-managed membership and expiry. URL flags or serialized approval fields cannot create this proof. Unknown credential submissions remain pending.

A terminal operator can leave a credential claim on the native journal ref before its issuer intent is published. Recover that exact claim with `reconcileUnsubmittedDatabaseCredential` from verified frozen source and the repository owner transport. Bind the original terminal operator evidence to an owner-created `fcos-database-auth-unsubmitted-evidence-v1` Deployment. The recovery verifies the claim and expired predecessor receipt, complete journal absence for the claim, and the pinned managed role's exact unchanged expiry. It fast-forwards one terminal child and appends its linked journal Deployment without issuing a login. An existing issuer intent, a changed role, or an uncertain terminal publication stops recovery. A controller must support the new terminal record before starting another credential operation.

If the issuer intent exists and native role expiry advanced, preserve the claim until the exact managed login expires. `reconcileExpiredDatabaseCredentialIssuance` requires the original owner-created intent, exact failed protected handover run, an owner-created native role observation, unchanged role configuration, and a fresh expired-role read. It records `issued_expired` with the HTTP outcome unobserved. It does not submit a login or close the separate handover. A prepared successor that stopped before staging still needs its original protected unstaged abort.

Ordinary stage and go-live jobs receive the dedicated metadata reader URL through `FCOS_RAPID_READONLY_DATABASE_URL`; they receive no Management credential. The source-owned reader has no role memberships, business-table write or create privileges, or executable privileged business routines. It can read only the coordinator fields and receipts needed for current release admission. The connection factory verifies the real TLS socket and native role/default transaction settings before opening a read-only transaction. Initial setup creates this separate credential without resetting the existing database password; its private value belongs in the pinned project Keychain item and protected CI secret slots. Quality and application build jobs remain credential-free.

Run:

```sh
npm run release -- prepare --candidate /absolute/clean/candidate --controller /absolute/clean/controller --baseline /private/baseline.json --public-environment /private/public-build.json --output /private/manifest.json
```

Dispatch `fcos-rapid-release.yml` with that exact manifest, canonical manifest SHA256 and candidate SHA. For an interrupted release, rerun the failed job or use `resume` with the successful original build run ID; the native producer and exact artifact are revalidated without rebuilding. A durable exact approval within its original lifetime is reused on the same native run. Platform-enforced approval boundaries still apply. `qualify` runs only credential-free quality/build. The default-branch dispatcher runs the independently frozen controller ref and selects checks from the actual Production-to-candidate Git difference and verifies that selection. Shared, authentication, financial, schema and unknown changes broaden coverage. Build credentials never reach candidate scripts. The pinned Vercel adapter generates Build Output API v3 once, inventories its bytes, and retains an immutable build ID separately from Vercel's observed deployment ID.

The stage job uploads the exact verified prebuilt output with Production runtime configuration and `--skip-domain`. It checks both static and server build identities, login, restricted access, affected desktop modules, and normal-role regression where required. Request-scoped restrictions are established before authentication/dispatch, including direct Supabase fetches, RPC/storage, exports, cron, notifications, background mail and credential refresh. Narrow authentication evidence is permitted through the existing governed harness. Missing coverage fails the stage.

The go-live job reads native approval, checks the live baseline again, promotes that same deployment ID and observes it for five minutes. Preparation targets 15 minutes; provider queue, approval wait, repair time, promotion and observation are measured separately. This target is a measurement goal, not a timeout that bypasses checks.

Incremental proof covers a verified owned-tree baseline, changed components, dependencies, test plan and resulting tree. A fresh native per-file inventory baseline can establish the first incremental release without unrelated historical full-suite jobs; existing complete-tree evidence remains a separate supported mode. An inventory review with different starting trees can pin an exact Git commit, tree hash, inventory hash and org ID for each of DEVEE, QAT and Production. Each difference must be covered by the reviewed manifest. The runner requires fresh native evidence of present bytes and expected absences before the first write and at each applicable bootstrap checkpoint. It is distinct from complete-tree deployment proof. Unknown/deleted/uncovered metadata requires explicit complete-tree qualification. Before a new validation or bootstrap submission, the runner converts only the exact reviewed source files and verifies the resulting Metadata API manifest, embedded members and round-trip definitions. It journals the package digest before sending the verified payload. The strict mirror, stop/refresh helpers, original eligible job IDs and all-or-none deployments remain mandatory. Never merge the shared draft PR automatically.

The hosted go-live already holds exact Production approval. Its Salesforce adapter runs one ordered pass and persists the same Production preparation checkpoint before bootstrap or deployment. It continues from that checkpoint under the existing write gates and reads original provider jobs after interruptions. The manual prepare/apply interface retains its explicit stop. For handover, prepare the exact quality artifact and all static inputs before collecting the administrator inventory. Independent provider reads are bounded and concurrent within each fresh audit. A complete administrator inventory is still required for the personal repository.

## Recovery and improvement

A Trading FX release stopped after a terminal QAT validation failure can use `tradingFxQatRecoveryReceiptId` only with an owner-recorded closure that binds the original database operation, mirror, QAT bootstrap and failed validation. The permitted source correction changes the sharing test fixture and its reviewed Salesforce source hash. The controller verifies the original Demo receipt against the original source, rereads the existing database result, and verifies original sandbox bootstrap packages, job results, permission assignments and native inventories. It validates the corrected metadata in DEVEE, publishes the complete corrected mirror, validates the corrected QAT package and continues through the usual protected Production gate. The new candidate requires its own build, staging proof and exact approval.


The runner invokes the existing supervising agent's event-driven improvement protocol on failures and uncertain outcomes. `handleReleaseObstacle` captures sanitized code-owned signatures once, preserves checkpoints, checks matching recipes once, and returns a typed supervisor work request for unfamiliar failures. Provider text never becomes executable instructions. Diagnosis normally targets 2–5 minutes; two unsuccessful attempts change strategy. Source repairs use another worktree and receive new source checks/authorization. Active controller execution is never hot-patched.

Only proof-backed, exact-precondition recipes execute. Original-operation reconciliation checks native operation/build/source/artifact identity and records the original result; it cannot resubmit a write. A still-unknown result stays pending. Failing recipes are disabled. `recordVerifiedLearning` records reproducible outcomes and regression evidence into the tracked registry from a separate worktree. Informational observations may document actual improvements; they grant no execution authority.

GitHub Deployment **objects** retain append-only intent/result payloads and hash-linked recovery history. Deployment statuses and seven-day build artifacts are display/transfer conveniences, not essential history. Financial evidence stays private. The shared Production concurrency group queues work without cancelling active writes. Native ownership and historical Salesforce/financial locks remain in force. Lost acknowledgements permit original-operation readback only. A rollback requires fresh native compatibility evidence, the recorded previous READY application, and this release still being current. Absent proof, preserve the usable checkpoint and report the dependency.

At phase/release completion report: **obstacle → correction → verification → measured time/calls saved → recurrence prevention**. Use “not measured” where no comparable before/after measurement exists. Report repair time explicitly. Notify sooner only for a meaningful dependency, exact approval or rollback.

## Initial activation and controller successors

The reviewed handover inventories actual workflows, controller pins, repository variables, Vercel auto-assignment, Deployment subscribers and original coordinator operations. It requires a current native database readback and no unresolved Production submissions. Other unknown outcomes and historical fences remain untouched.

`fcos-rapid-handover.yml` runs the trusted setup adapter behind the existing protected environment. Before issuing a database credential, setup checks native overlapping-workflow liveness and the current Production target. Each prepare, ownership check, finalization and activation checkpoint uses a fresh native database context, closed before staging or browser waits. An interrupted finalized handover is reconciled against its original private and GitHub receipts and resumes activation without another stage or final receipt; a missing acknowledgement remains readback-only. The explicit `activate` handover command uses that same verified recovery path. It reversibly freezes the old release control, stages and tests the qualified artifact without a live alias, retires overlapping entrypoints, rereads them, and finalizes a permanent old-writer guard and append-only handover receipt. Activation occurs only after successful native setup. Failure leaves a documented reversible checkpoint; unknown provider submissions are reconciled before any retry. The runner checks the native receipt/run/review before every provider mutation. A new controller hash requires a separately qualified successor handover, never an invented approval flag.

If the initial controller cannot satisfy the inherited authenticated-browser PR gate because no native Preview exists, the source-owned one-time `scripts/rapid-release-bootstrap.mjs` adapter first requires exact-source native quality, reviewed complete app inventory and a quiescent native coordinator. Its atomic bootstrap claim permanently freezes the old control and appends private receipts before a single Git-source **Preview** submission. It never assigns the live domain. Readback must find the original deployment and genuine `vercel[bot]` Preview proof before the existing protected authentication workflow runs. This installation bootstrap is separate from ordinary prebuilt application releases. A pending or lost submission permits readback only; it does not authorize another deployment or unfreezing the old writer.

Historical hosted release/bootstrap/cutover documents and canonical `.fcos-cli/release-state.json` remain recovery references for their original owners. They do not activate the rapid route. Do not delete old journals, lift old fences, resolve unknowns by assumption or operate two writers.

If the first frozen controller needs a repair before initial handover, retain its original bootstrap plan, permanent control fence, four private receipts and actual failed checks. ## Qualification

`npm run release:qualify` covers frontend-only selection, staging identity/isolation, exact artifact promotion, lost acknowledgements, interruptions, stale/expired validations, concurrent operations, recipe mismatch/failure, resumed prerequisite smoke, exact approval and compatible rollback. The complete product suite and required compatibility/migration/performance checks also apply to the final source. Local fixtures are not hosted evidence: record actual setup qualification, browser coverage and provider identities before activation.

Trading FX requires a separate Xero test-company qualification before the combined database and Salesforce release. Retain provider identity, exact readbacks and recovery evidence privately. The repository owner records the exact application SHA, source digest, migration digest and per-check evidence digests in a non-Production GitHub Deployment receipt. The manifest pins that receipt's ID and digest. The controller checks the original GitHub owner and all required case digests at staging and go-live. It receives no Xero test credentials. The protected Production decision still authorizes the exact tested release.

A successor plan is built from the latest finalized database receipt and the exact native active-handover pointer. Both must agree; an unactivated final, another open handover, or an unresolved Production operation blocks preparation. The read-only rapid journal audit binds its complete evidence digest and zero pending provider intents into the reviewed plan. Only the exact setup qualification manifest is excluded as it advances; older staged application releases awaiting a decision remain unchanged.

Successor preparation and abort leave the legacy control permanently frozen. Qualification remains stage-only under the same global concurrency group. Finalization appends a new numbered receipt linked to its predecessor, then fresh database/native checks permit the activation pointer to switch. The previous controller hash immediately fails the normal execution verifier. An unknown GitHub receipt submission remains pending for original-operation readback; it never permits a second blind submission. The initial guard schema has not been applied live; an existing different schema requires separately reviewed migration evidence.

Before qualified native activation, the inherited PR authenticated-browser gate still requires its original trusted evidence artifact and may remain pending or fail without it. It is not hosted acceptance. After activation, that overlapping legacy gate retires; the exact rapid stage-and-smoke authentication and normal-role coverage remain mandatory before the protected decision.

Candidate module coverage is parsed from the literal `APP_MODULES` declaration without evaluating application code and rechecked before build. Shared, authentication, Salesforce and unknown changes require all actual candidate modules; scoped modules outside Dashboard/Markets also require the approved normal role. Unknown or moved module paths fail before credentials. Each maintained module needs a real authenticated read and desktop business surface; connector/configuration scopes are labelled precisely, never presented as financial verification. Stage-only Hedge Desk, dispute and holiday reads suppress maintenance/cache writes while canonical behavior stays intact.

The protected setup records the observed native review and qualification in both an owner-created GitHub Deployment receipt and the append-only private database receipt. The publisher is recorded separately from the actual reviewer; a bot-created copy cannot authorize a controller. Old Actions histories are diagnostic, not continuing authority. Every effectful provider admission rechecks the latest finalized private receipt, exact evidence/controller, unchanged permanent control fence and guard, and unresolved historical operations using the pinned read-only TLS connection. A missing receipt or changed guard stops execution without recreating history.
