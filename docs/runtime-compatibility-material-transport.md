# Exact04ee runtime material transport

This optional data transport removes the need to commit each new context and pair of reviews. It grants no Preview, Production, signing, provisioning, finance, lease or credential authority. Existing activation flags and actual GitHub environment review still apply. Source changes require fresh exact action admission; an earlier consumed approval cannot authorize this code.

The protected environment may hold two public variables:

- `FCOS_RUNTIME_COMPATIBILITY_MATERIAL_TRANSPORT=run-artifact-v1`
- `FCOS_RUNTIME_COMPATIBILITY_MATERIALS`: a JSON pack of at most 49,152 UTF-8 bytes.

The pack has exactly `schemaVersion: 1`, `kind: "fcos_exact04ee_runtime_material_pack"`, `binding` and `materials`. `materials` contains exactly `context`, `root` and `independent`, each an **original JSON text string**, including its original whitespace and timestamps. This preserves the material SHA-256 hashes and creator-returned IDs. The binding has these ordered fields: `repositoryId`, `environmentId`, `harnessSha`, `candidateSha`, `sourceDigest`, `lockHash`, `candidateTreeHash`, `previewControlRevision`, `configurationRevision`, `runId`, `runAttempt` (1) and `workflow`. Values must come from the exact source/control configuration and actual current protected first-attempt run, never from a historical receipt. Repository-level definitions of either variable are rejected as ambiguous.

The fixed main-harness producer authenticates the pinned operator read token, protected branch, actual run/attempt/job/environment approval and cryptographically verified GitHub Actions OIDC before reading the pack. It independently validates the original context and both distinct reviews, repeats mutable authentication and pack reads, and uploads only the data pack in one bounded immutable artifact. A durable same-run local attempt marker prohibits a repeated upload after an uncertain outcome. It reads no Vercel/provider/private signing material and cannot issue a selection or grant.

Each producer step runs the local `node24` JavaScript action at `.github/actions/runtime-compatibility-materials`, from the protected `trusted` checkout for Preview/release and the protected workspace root for normal-role. Its descriptor invokes the existing producer directly, with no wrapper arguments. The descriptor is part of the reviewed control/harness closure. GitHub's JavaScript action handler injects `ACTIONS_RUNTIME_TOKEN` and `ACTIONS_RESULTS_URL` for the installed artifact SDK; ordinary shell `run` steps do not receive that runtime. Missing runtime variables fail at the bounded `artifact_runtime` phase before provider reads, the durable attempt marker or any upload. Their values and the results URL are never logged. This runtime check grants no provider or execution authority and changes no OIDC, source, review or freshness requirement.

The fully serialized JSON wrapper must fit the decoder's 65,536-byte limit before the attempt marker or upload. After authentication reads, a fresh actual clock check enforces the original OIDC, run, job, step, provisioning and review deadlines before the marker and immediately before the single SDK upload. After the single SDK-finalized upload, GET-only reconciliation retries absence for at most ten observations, with 500 ms waits and a five-second deadline further capped by those same original clocks. It then checks the exact returned SDK ID/name/digest/size against both list and direct artifact metadata and the strict archive. Duplicates, mismatches, corrupt data and unclassified read errors fail immediately. The fixed adapter redacts HTTP error classes, so the producer never guesses that an unclassified failure is transient or retries an upload.

Immutable artifact publication is itself a live GitHub provider write. Before any future workflow dispatch or resume, the root orchestrator must hold the accepted coordinator guard and root-owned shared lease explicitly covering this data-only upload. The producer neither acquires nor steals that lease. Existing hosted Preview/private execution obtains its action claim later, after this producer step; that later claim does **not** supply the earlier upload boundary. Therefore this lease coverage is an explicit orchestration prerequisite, and source review alone authorizes no upload.

The live collector independently requires the exact successful producer step, actual current protected run/attempt/job/actor/reviewer/environment, exact archive identity/digest/size and bounded one-file schema. It revalidates source/control/configuration binding and all original material clocks before minting its existing opaque admission. Runtime mode present with missing, malformed, ambiguous or unproved input fails closed. Static Git material compatibility remains available only when both variables and this run's material artifact are genuinely absent. The verification-only authority path continues its separate historical provenance behavior.

The runtime contract hashes the original context/root/independent bytes under an explicit runtime domain. Each workflow independently authenticates its own run-bound pack/artifact, while identical material bytes retain the same contract across Preview build receipts, normal-role and release. Native private approval and grants separately bind the exact current run, source, controls and this contract; no authority transfers with a receipt. Preview readback has a data-only producer too and retains its existing read-only purpose.

The original 45-minute provisioning, 30-minute material/dispatch, 1,800-second run and 600-second receipt/grant clocks remain literal. Capture/publication time cannot renew them. No refresh, reprovision, retrospective review, timestamp restoration or old-record revalidation policy is introduced. All fifteen compatibility modules, exact Preview and observed Production requirements remain mandatory.

Normal-role exact04ee additionally requires the dedicated pinned-operator `FCOS_RELEASE_GH_TOKEN`. The existing hosted `GITHUB_TOKEN` remains the legacy transport and cannot satisfy this operator check. Public metadata on 11 October 2026 confirmed the dedicated secret is absent from the normal-role environment and repository; provisioning it is a separate later dependency. This local change neither reads nor copies or creates any secret.

Only immutable archives are cached, by exact artifact ID/digest/harness and authenticated reads transport within one invocation. Actor, environment, approval, job/step, current source/run, variable and artifact metadata reads stay fresh. No provider writes, uploads, signing or workflow dispatch were executed during local implementation or tests.

A producer failure emits one bounded fcos_runtime_material_failure record with only an allowlisted phase and last attempted fixed GET endpoint class, numeric HTTP status and CLI exit code. OIDC diagnostics identify only token-request or signing-key discovery phase/status. Raw exceptions, provider responses, request URLs, token/claim values, CLI arguments and material text are never logged. The diagnostic neither retries a failed read/upload nor supplies missing identity or authority evidence. Unknown failures remain fail-closed; the original timestamps and exclusive attempt marker are retained.


## Durable setup v2

The protected environment can explicitly select `FCOS_RUNTIME_COMPATIBILITY_MATERIAL_TRANSPORT=durable-setup-v2`. Its material input must then be a schema 2 `fcos_exact04ee_setup_material_pack`; mode/format mismatches refuse admission and never fall back to static material. The existing v1 contract and clocks remain unchanged.

V2 separates reviewed setup from current execution. The context uses schema 2, kind `fcos_exact_04ee_setup_context` and the content hash of `config/runtime-compatibility-setup.json`. It retains all v1 source/control/record fields and adds `setupExpiresAt`, `cleanupDeadline` and `recordMetadata`. Metadata contains the exact non-secret tenant/client/attachment rows, including IDs, types, branch, targets, creation/update timestamps and provenance comment. Root and independent schema 2 `fcos_exact_04ee_setup_material_review` records bind the original context bytes and keep their original review times.

The original setup expiry must be no later than its original cleanup deadline or 24 hours after provisioning. Publishing, reviewing or reading setup cannot move those clocks. The durable pack binding keeps repository/source/tree/lock/harness/control hashes and `setupContractSha256`, but omits environment ID, run ID, attempt and workflow. Those execution identities remain in each independently authenticated producer envelope. The same unchanged pack can therefore serve the Preview, normal-role and compatibility workflows without recreating settings or republishing a run-selected pack.

After GitHub's configured approval, the actual first-attempt protected job start establishes the 30-minute execution window. Dispatch time remains original identity/order evidence. Fresh OIDC, approved environment, exact actor, current source and immutable artifact authentication remain mandatory. Fresh complete Vercel metadata must exactly match every pinned setup field before creating an intent and again before submitting the Preview POST. Drift stops execution; no automatic repair, rotation or upsert is available.

A completed Preview's immutable successful-run receipt can be reused by later admitted verification while setup is valid and fresh deployment/version/metadata reads still match. This historical evidence cannot mint a new CREATE capability. Original CREATE intents and canonical consumption remain fresh and once-only. V2 attestation needs its explicit schema 2 action and setup-policy hash; v1 signing approval cannot transfer. Token expiry, private readiness, signing consent, ten-minute receipts, action reviews, shared canonical lease, permanent nonces and uncertain-outcome GET-only recovery are unchanged.

Compatibility release coordination uses binding schema 3 for this route; existing schema 2 identifies the earlier exact04ee contract. This does not extend Production quality/browser evidence deadlines, authorize Production, renew a credential, change financial authority or dispose of an uncertain operation. Installation and actual provider execution require their current exact authority and verified evidence. No existing private session is transferred to v2.
