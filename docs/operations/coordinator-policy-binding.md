The coordinator policy compiler derives the qualification policy from the already admitted manifest and setup. It changes only bootstrapSha, callerWorkflowSha, jobWorkflowRef, jobWorkflowSha and setupSha256. Repository, ref, candidate, Production allowlists and all other policy values stay byte-equivalent as canonical JSON. An already matching policy produces no changes. This is a same-source configuration repair, not a general admission, controller publication or credential action.

The maintained local entrypoint is:

```
node scripts/hosted-coordinator-policy.mjs compile INPUT.json INPUT_FILE_SHA256 NEW_BINDING.json
node scripts/hosted-coordinator-policy.mjs check CHECK.json CHECK_FILE_SHA256 NEW_RECEIPT.json
```

Each input has kind `fcos_coordinator_policy_command_v1`. Compile takes physical absolute hash references `{path,sha256}` named `manifest`, `setup` and `previousPolicy`, plus independently reviewed `coordinatorProjectId`, `coordinatorSourceSha256` and `preservedConfigurationSha256`. The latter is the existing preservation fingerprint of configuration/settings excluding the one policy value being repaired; it is not a request to read or export credentials. Check takes the same inputs plus hash references `binding`, `observation` and `dispatchRequest`, and the independently frozen `dispatchRequestSha256`. Outputs are new local0600 files; the command refuses overwrite. It performs no network call or provider mutation.

The public module exports `compileCoordinatorPolicyBinding(inputs)` and `assertCoordinatorPolicyPreflight(inputs,{now:Date.now})`. Check requires a callable live clock and the existing90-second freshness bound. The binding cannot provide its own replacement project/source/configuration expectation. The existing isolated coordinator project is independently bound; it is not assumed to be the application deployment project. The owner-readback adapter must supply genuine fresh provider observations with native response fingerprints; a hash or self-labelled JSON object does not independently attest provider identity or grant authority.

The observation kind is `fcos_coordinator_dispatch_observation_v1`, `unknown:false`. Each of `github`, `coordinator`, `variables` and `health` contains its actual `observedAt` and `rawResponseSha256`:

- `github`: repository/repositoryId, operatorLogin/operatorId/repositoryOwnerId, ref, callerSha/callerWorkflowRef, controllerSha/jobWorkflowRef, branchProtected/lockBranch/enforceAdmins true and allowForcePushes/allowDeletions false.
- `coordinator`: projectId/teamId, target `preview`, readyState `READY`, deploymentId/url, sourceBundleSha256/preservedConfigurationSha256 and the freshly observed whole project policy.
- `variables.values`: exactly FCOS_ADMITTED_RELEASE_SETUP as canonical JSON, FCOS_ADMITTED_RELEASE_SETUP_SHA256, FCOS_HOSTED_QUALIFICATION_ADMITTED and FCOS_HOSTED_COORDINATOR_URL.
- `health`: method `GET`, exact coordinator origin `/health`, status200, redirected false, cacheControl `no-store`, and exact body `{kind:"fcos_coordinator_health_v1",policySha256}`. Its effective digest must match the compiled whole policy. Project environment metadata alone cannot substitute for the loaded service policy.

The checker binds the exact existing workflow-dispatch request. It supports the original frozen plan by comparing every construction field with the immutable manifest (schema/stage/mode/releaseId/branch/sourceProfile/changes/scope/runtime/migration), and the caller's supported resume_manifest path by exact parsed manifest equality. The independent request hash preserves exact input bytes, including existing JSON key order, without requiring reserialization. Both retain candidate/source bindings and disabled Xero recovery. Rerun routes, mixed plan/resume, changed manifest, warm modes and extra financial inputs refuse. This does not change the current caller86/controllerb8/setup4adc or the original frozen plan request30e23.

Root's verified native execution adapter must call check before claiming/submitting its exact dispatch and use only the matching dispatchRequestSha256 while the original observations remain fresh. This module does not turn a successful receipt into write authority or clear a consumed/unknown operation. An existing unknown/refused provider action still stops all follow-on RPCs and requires its original separately admitted owner readback. The server retains OIDC verification and run_attempt1; each new dispatch requires its real finite admission. No wildcard refs, trust-on-input principals or auto retries are introduced.

The older source-upgrade six-action publication contract remains intact and historically scoped; this helper does not claim it accepts arbitrary new tuples. It removes manual five-field copying and catches the complete source/setup/policy/service/URL mismatch before consuming a workflow. Genuine changes to source or policy still require the existing owned configuration publication and readback. Existing proof hashes and original times remain reusable only for unchanged dependencies. Compatibility and application remain separate Production stages with their existing qualification, financial, identity, rollback and exact human approval gates.

Focused verification uses `node --test tests/hosted-coordinator-policy-binding.test.js tests/hosted-coordinator-health.test.js`. The compiler tests include actual CLI compile/check/refusal, every stale policy pin, partial configuration, stale loaded health, wrong source/URL/settings, unknown/expired observations, a fixed numeric-clock refusal, new-dispatch-only routes, and preservation of all other policy fields. Native HTTP health tests exercise the server separately. These local checks do not establish provider identity, actual deployment, registration, Preview qualification or Production readiness.
