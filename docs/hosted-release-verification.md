# Hosted release verification v2

`config/release-checks-v2.json` is the command and prerequisite source for the new hosted workflow, the local runner and its proof validators. The historical `candidate-quality.yml`, f457 admission and v1 receipt contracts remain separate and unchanged.

A source profile is explicit. `frozen_04ee` binds `04ee3425aac7a49089eda781eb3c976aea1f6785` and preserves its complete original quality scope: full Node unit/integration suite, lint, both typecheck projects, compatibility, Graph source, the actual four browser fixture suites, build, migration replay and all twelve database categories. `historical_f457` includes its two additional fixture suites. `controller_v2` verifies the new controller code and Python ledgers; it cannot substitute for the frozen business candidate's fixture/database evidence. Missing required files cause failure. Applicable required checks are derived from `requiredReleaseChecks(manifest, sourceProfile)`; they are never silently skipped.

The fixed build commands preserve the actual candidate scripts. Frozen business candidates run methodology asset generation, hosted FCUNO environment verification, version generation and Vite. The current controller profile runs version generation and Vite. The runner never resolves an executable command from candidate `package.json` scripts or from a candidate copy of the manifest.

## Runner and report interface

Run the trusted controller's script against a separate exact candidate checkout:

```sh
node controller/scripts/hosted-release-checks.mjs \
  --controller-directory /absolute/controller \
  --controller-sha FULL_IMMUTABLE_CONTROLLER_SHA \
  --candidate-directory /absolute/candidate \
  --candidate-sha FULL_IMMUTABLE_CANDIDATE_SHA \
  --source-profile frozen_04ee \
  --group code \
  --evidence /absolute/outputs/code.json
```

`--group code|fixtures|database` selects independent deterministic jobs. `--check id,id` selects admitted checks and `--phase deterministic|final` selects a phase. `--dependencies report.json,other.json` supplies original prerequisite reports. `--cache report.json` supplies deterministic results to consider for exact reuse. CLI exit codes are 0 for passed, 1 for failed, and 2 for `waiting_dependency`. A missing or pending prerequisite is `waiting_dependency`, including absent live browser or server-bundle proof. It cannot become a skipped required check or a false failed live test. Reports are atomically saved after each check and at completion.

Reports use `schemaVersion: 2`, `kind: fcos_hosted_release_checks`, common binding fields and `checks`. Each check has `checkId`, `status`, `binding`, original `startedAt`/`completedAt` and the complete admitted command results. Waiting records also have `missing`. Bindings contain:

- Exact candidate SHA, immutable controller SHA, source profile and manifest SHA256.
- `sourceInputsSha256`: SHA256 of the JSON-serialized sorted `[trackedPath, SHA256(actualBytes)]` pairs, excluding the two generated build receipts. This is a verification input digest. Canonical deployment `sourceDigest` remains the separate `collectBuildProvenance` deployment-source-v1 value and must be independently admitted by the publisher.
- Actual package lock, installed dependency lock, candidate configuration and relevant check input hashes.
- Actual Node and Python versions, OS and architecture, plus the admitted command hash.
- Actual artifact hashes for client performance and strict final server performance.

`collectReleaseCheckSource`, `collectCheckBinding`, `checkBinding`, `requiredReleaseChecks` and `evaluateCheckEvidence` are exported for the trusted publisher. Candidate source and the admitted controller implementation must be clean. Node major must be 24. Both repository remotes must match the pinned FCOS repository. Credential-bearing tracked paths are rejected before hashing.

## Trust and final acceptance

Candidate execution requires a separate runner with no protected environment, no OIDC write permission, no provider or controller credential, no persisted checkout credential, and no credential-bearing controller files. Environment sanitization is additional containment, not a sandbox against reading sibling files or processes. Installation and candidate tests must use the same separate-runner boundary. The runner supplies a temporary HOME and explicit non-secret environment, fixed disposable localhost database targets and no inherited provider variables. Browser fixtures may execute candidate Vite configuration; they must remain inside this boundary.

A raw candidate report is untrusted. A distinct trusted publisher must independently verify source admission, actual workflow/job outcomes, immutable controller identity, artifact digest and complete required check coverage before accepting it. `evaluateCheckEvidence` requires an explicit `validateExternal(check, record)` callback for volatile provider evidence; the CLI cannot grant that authority merely by loading a JSON file.

Deterministic cache reuse requires an exact binding, complete successful admitted command list and valid original timestamps. Builds recreate their output and are explicitly noncacheable. It preserves the original record verbatim. It never refreshes an old timestamp or relabels an old source/controller result. Live Preview binding, FCUNO, server artifacts and browser proofs remain volatile and must satisfy their original 30-minute freshness boundary as well as independent provider validation.

Restricted browser proof and normal-role proof are distinct required records. Normal-role proof requires real loaded data for all fifteen modules: Dashboard, Markets, Review, Disputes, Buyer Invoices, Unofficial Compensation, Incoming Payments, Cashflow Forecast, Brokers, Master Contracts, Special Terms, Hedge Desk, Xero Portal, Email Router and Settings. Duplicate, absent, heading-only or unavailable module observations fail coverage validation. No live browser credentials enter candidate commands.

`server_performance` always sets `FCOS_REQUIRE_SERVER_BUNDLES=1` and binds both `dist` and `.vercel/output`. Missing universal or dedicated Vercel function bundles fail this check. Frontend-only performance is a separate deterministic check and cannot satisfy final acceptance. `final_acceptance` requires every applicable deterministic check plus fresh Preview, FCUNO, server-bundle, strict performance, restricted-browser and normal-role evidence.

## Salesforce durable resume

The existing `salesforce:deploy:all` entrypoint now journals each environment's bootstrap, validation, deployment and permission stages under `.fcos-cli/salesforce-promotions/<binding>.json`. Writes use an exclusive process lock, atomic rename and file/directory fsync. A dead process lock can be reclaimed; an active process blocks concurrent promotion.

The binding includes the complete authoritative Salesforce tree hash, reviewed manifest and bootstrap bytes, Salesforce connection policy, test level/classes and check-only mode. Frontend, orchestration script and documentation changes do not invalidate successful Salesforce jobs for an unchanged binding. Source, manifest, Salesforce configuration or test assumptions changing creates a new journal and starts from DEVEE.

Every mutation rechecks the exact source and pinned org/username/sandbox identity. Submitted jobs use `--async`; the job ID is durably saved before waiting for an all-or-none successful report. A successful saved validation is quick-deployed rather than revalidated. Resuming rechecks upstream successful deployment reports and permissions; invalid or failed upstream reports stop downstream mutation. A submission with an uncertain outcome and no recorded job ID stops safely for job-ID reconciliation and never silently submits a duplicate.

The sequence remains DEVEE, exact byte-equivalent shared source in an open draft PR, QAT, Production. DEVEE's fresh deployment proof gates shared publication. Shared mirror verification is required before each downstream environment and again at completion. The shared PR is never merged by this command. Schema cutover bootstraps each environment first, uses `NoTestRun` in DEVEE/QAT and `RunRelevantTests` in Production, assigns data permissions, then validates the complete package once with `RunLocalTests`.

Financial and release authorization gates remain outside this journal. A local journal is a continuation record, not permission to promote and not a substitute for current provider reports. No provider writes or live authentication are needed to run the new tests: they exercise the actual entrypoints through temporary repositories and local process stubs, including a killed process and durable resume.

## Hosted browser and renewable diagnostic identities

`scripts/lib/hosted-release/browser.mjs` exports `runHostedBrowser({ manifest, preview, mode, env, ...dependencies })`. `mode` is `restricted` or `normal_role`. The independently verified Preview must bind the pinned project/team, deployment ID, exact candidate and manifest hash. The adapter rechecks provider metadata, `app-version.json`, clean source provenance and the exact expected read-only runtime before obtaining either test identity. A trusted workflow may supply a current provider-proof reader; the default uses only pinned Vercel GET endpoints and the independently enrolled read-only Integration credential below.

### Vercel read Integration enrollment

Verification and browser jobs use `FCOS_HOSTED_VERCEL_READ_TOKEN`, with exactly Integration Project Read, Deployment Read and Integration Configuration Read. Personal project tokens have no documented read-only selector and cannot substitute for this credential. Preview/Production writer PAT admission, finite expiry, project confinement and protected execution remain unchanged. Read jobs receive no writer-token variable or OAuth client secret, expose no deployment/write methods and execute no Vercel CLI command.

The immutable admitted setup's `verification.vercelReadCredential` has `schemaVersion:1`, `kind:'fcos_vercel_read_integration'`, the high-entropy bearer `bearerSha256`, exact `clientId`, `integrationId`, `configurationId`, `teamId`, `projectId`, the three exact `scopes`, original numeric `issuedAt`, finite reusable `notAfter`, `oauthExchangeReceiptSha256` and `rootAcceptanceSha256`. Qualification refuses a missing binding. These are public metadata, not the bearer, OAuth code or client secret. `notAfter` is a local admission horizon limiting credential use across runs; it does not assert provider-enforced token expiry and creates no per-run consent or signing window. Provider revocation/retirement remains the setup owner's separate lifecycle action.

One-time privileged setup must retain and independently review the ORIGINAL native `POST /v2/oauth/access_token` receipt and actual configuration readback before admitting the fingerprint. A helper-generated fingerprint/assertion alone is not acceptance. `setup.vercelReadCredentialAcceptance` is `{json,sha256}` containing the exact public root-review JSON bytes; its hash must equal `rootAcceptanceSha256`. The review has `schemaVersion:1`, `kind:'fcos_root_accepted_vercel_oauth_exchange'`, `accepted:true`, `reviewerId:'/root'`, canonical `operator`, original `reviewedAt`, `originalExchangeReceiptSha256`, `configurationReadbackSha256`, and `credential` containing the same nine credential fields from `bearerSha256` through `notAfter`. Both proof references remain anchored in the existing admitted setup/source hash. The receipt hash preserves the original operation; it does not by itself prove provenance. Private enrollment and the real root review remain setup-owner work.

The reader compares the in-memory bearer fingerprint, verifies admitted setup/hosted source context, then freshly GETs its exact configuration before each provider read. It requires matching installation/integration/team/owner, `projectSelection:'selected'`, only the FCOS project, the exact Read scopes and an active, undeleted installation. Configuration GET proves the current installation policy; the admitted ORIGINAL-exchange fingerprint closes broader-token substitution. Missing/changed review, different bearer, changed scope/project/status or expired `notAfter` fails closed. Only fixed project/deployment GET routes are exposed. No unsafe write probe or undocumented token-class inference is used. See [configuration schema](https://vercel.com/docs/rest-api/integrations/retrieve-an-integration-configuration) and [Integration permission table](https://vercel.com/docs/integrations/create-integration/vercel-api-integrations).

Browser jobs must carry no coordinator token, OIDC write identity, Vercel write credential, Production credential or other provider authority. Restricted and normal credentials belong in separate jobs. The adapter rejects both roles in one job and rejects imported `FCOS_NORMAL_ROLE_STORAGE_STATE_BASE64`. Chromium's process environment is also reduced to non-secret runtime variables. No candidate code runs under Node in these jobs; the browser executes the verified remote candidate, and the fixed test code comes from the admitted controller.

Required setup is explicit:

- `FCOS_HOSTED_BROWSER_ENABLED=true` and existing origin-scoped Preview protection access.
- Restricted: a complete dedicated `FCOS_HOSTED_RESTRICTED_EMAIL`/`FCOS_HOSTED_RESTRICTED_PASSWORD` pair, or the existing repository `FCOS_E2E_EMAIL`/`FCOS_E2E_PASSWORD` pair forwarded only through named restricted fallback inputs. Both fields select the same complete pair inside the restricted matrix job; a partial dedicated pair selects neither dedicated field, and an incomplete fallback pair yields no identity. The normal/runtime jobs receive neither fallback field. No credential is decrypted, relocated or re-entered. The real `authContext` must still be the pinned active viewer/CI identity, Dashboard and Markets only, with every capability false.
- Normal: dedicated `FCOS_HOSTED_NORMAL_EMAIL`/`FCOS_HOSTED_NORMAL_PASSWORD`, `FCOS_NORMAL_ROLE_APPROVED_EMAIL` and `FCOS_HOSTED_NORMAL_EXPECTED_ROLE`. The real `authContext` must match the approved existing active non-CI identity and role, with all fifteen existing module accesses. The adapter does not assign roles, provision users or widen access.
- Frozen04ee: an independently verified v2 source/observation receipt and an explicitly reviewed signer adapter. The receipt binds candidate/controller, canonical source, lock/configuration and manifest hashes. The signer adapter must prove the exact relevant source hashes and collect the existing bounded synthetic signer probe without fetching an attachment. Missing signer/source admission is reported as its exact `waiting_dependency` input; it is not disabled.

`loginHostedFcuno` follows the pinned FCUNO `/admin` Username/Password/Login flow and validates the application's own `authContext` response. It creates a fresh dedicated test session each run, filters state to the exact candidate origin and keeps the session bearer in memory. Issuer and exact `/admin` location are checked before either credential field is filled. Temporary restricted state and configuration are private, generated within the run and removed on completion or failure. They are not imported or reused per deployment.

The restricted adapter reuses the controller's workspace, Dashboard and API-denial suites with legacy resolver/global setup disabled, no auth-setup rerun, desktop only, no trace/screenshots/video and no skipped tests. Frozen04ee normal verification reuses the complete specialized v288 module loop, real response settlement, workspace preference read, same-context guardian lock and telemetry exclusion. The legacy harness defaults remain unchanged. Hosted source, resolver, fresh authentication, browser and evidence writer are narrow explicit injection points. All15 coverage, zero escaped mutations, explicit isolation release and signer evidence are checked before returning a passed result.

The raw result has `schemaVersion: 2`, `kind: fcos_hosted_browser_raw`, `id`/`checkId`, status, manifest/candidate/controller/deployment/source binding, `inputsSha256`, and the original actual `capturedAt`/`completedAt`. Its sanitized `result` contains identity category, module IDs, `actualData`, `unexpectedWrites`, and public isolation/signer facts when applicable. It contains no bearer, password, session state, screenshot, private response or raw error. A trusted publisher still verifies actual job and artifact provenance. Missing setup returns `waiting_dependency` with exact `missing` keys; failed real binding or coverage returns a fixed safe failure code.

`createHostedRuntimeTokenProvider` is separate. It requires `FCOS_HOSTED_RUNTIME_EMAIL`/`FCOS_HOSTED_RUNTIME_PASSWORD`, an approved existing `FCOS_HOSTED_RUNTIME_EXPECTED_ROLE` of `administrator` or `general_manager`, and a trusted callback proving the exact target/provider/source before login. It verifies active non-CI real `authContext`, performs the same fresh FCUNO login and returns only an in-memory token to the trusted runtime collector. It never exports a key, reads Keychain or publishes a token artifact. This diagnostic identity must remain separate from restricted and normal browser jobs.

The specialized normal-role report does not prove Nom B filing, live fixture outcomes or Salesforce source equivalence. Its Dashboard read is not a substitute for the separate mandatory Nom B proof. Deterministic Nom B fixture/database checks remain in the versioned manifest; live Nom B evidence needs its own relevant Salesforce-tree, fixture and environment binding.

Dependency evidence can be imported through `importAcceptedNomB` in `scripts/lib/hosted-release/dependencies.mjs`. This accepts the historical `root_actual_exact04ee_disposable_nom_b_acceptance` packet only through an independently verified, manifest-bound migration handoff. The handoff pins eight SHA256 references: `acceptance`, `reuseDecision`, `liveEvidence`, `desktopEvidence`, `scope`, `admission`, `dependencies`, and `cleanup`. `readArtifact({sha256})` must read immutable admitted bytes; JSON paths are never followed. Every original test/readback reference is also checked against its actual bytes. `verifyHandoff` must independently return the matching `handoffSha256`, `manifestHash`, `verified:true`, and `financialAuthority:false`; accepting caller declarations is insufficient.

The reviewed handoff binds `candidateSha` to the current manifest and `originalCandidateSha` to the historical frozen candidate; a new candidate alone does not invalidate unchanged relevant behavior. The reviewed handoff supplies `relevantInputs` with exactly `sourceSha256`, `harnessSha256`, `salesforceSourceSha256`, `fixtureSha256`, and `environmentSha256`. `measureInputs` performs fresh read-only measurement and returns `{readOnly:true,capturedAt,inputs}`. Each value must equal the original reviewed assumption; `measureDependencyFiles` hashes reviewed paths without executing candidate code and rejects traversal and symlinks. The original NomB packet uses a relevant application fingerprint (`ccb81ab8…`), which differs from the build provenance source digest. The migration review must establish that mapping and the original Salesforce tree, fixture and environment assumptions from the retained deployment/schema/automation records. A missing mapping or fresh environment read is setup work, never a reason to substitute all15 browser coverage or to recreate the cleaned fixture. The raw report retains the original core `completedAt` and explicitly describes `disposable_devee_nom_b_synthetic` coverage with no deployed-Preview or financial authority claim.

`collectFinancialPreservation` takes a separately verified `fcos_release_preservation_membership` with `schemaVersion:1`, the pinned Supabase `project`, exact `manifestHash`, and `tables:[{table,keyColumn,keys,expectedRowsSha256}]`. The owner must review complete membership and baseline hashes; local private54 fixture acceptance alone is not a live baseline. The collector connects using `FCOS_HOSTED_PRESERVATION_DATABASE_URL` as the dedicated `fcos_release_observer` role on the pinned direct database host with `sslmode=verify-full`. It verifies no role memberships, superuser/RLS bypass, table write grants or callable security-definer functions, then reads full keyed rows inside a repeatable-read READ ONLY transaction. Changed or missing rows fail. Reports contain only aggregate counts/digests, preserve no credential or financial values, and remain fresh volatile evidence. Missing credentials, reviewed membership or legacy import inputs return `waiting_dependency`; invalid evidence fails closed. Both APIs return raw reports for the trusted publisher and never mint a publisher identity.

The separate raw producer is `node scripts/hosted-release-dependencies.mjs`. Its hosted job name is `release / dependencies / before` or `release / dependencies / after`, selected with `FCOS_VERIFICATION_PHASE`. It uses the existing hosted source/session admission with `requireOidc:false`, rejects OIDC and broad provider credentials, reads candidate files as data, and returns both mandatory dependency results. Upload its `dependencies.json` as `fcos-<releaseId>-dependencies-<phase>` from the successful `Run admitted checks` step. The root workflow must call `publishDependencies` from its independently admitted publisher job. That function fetches the actual job, run, archive and digest through the common artifact collector and strict publisher; the raw producer never appends coordinator evidence.

The admitted manifest's setup definition is `dependencies:{schemaVersion:1,nom_b:{handoffSha256,artifactsSha256,recipeSha256},preservation:{membershipSha256}}`. An independent setup review must admit these hashes, including the cross-format NomB measurement mapping; JSON schema validity is not that review. The corresponding files are `FCOS_HOSTED_NOM_B_HANDOFF_FILE`, `FCOS_HOSTED_NOM_B_ARTIFACTS_FILE`, `FCOS_HOSTED_NOM_B_RECIPE_FILE`, and `FCOS_HOSTED_PRESERVATION_MEMBERSHIP_FILE`. Handoff and membership file bytes omit `manifestHash` to avoid a circular hash dependency; the loader attaches the admitted manifest hash in memory. The handoff also pins `measurementRecipeSha256`. The immutable artifact file is `{schemaVersion:1,kind:'fcos_immutable_dependency_artifacts',artifacts:{'<sha256>':'<base64 bytes>'}}`, including the original test and readback files. The trusted module independently pins the eight accepted legacy history hashes; selecting a new setup hash cannot manufacture another accepted original test.

The concrete NomB measurement recipe has `schemaVersion:1`, `kind:'fcos_nom_b_readonly_measurement_recipe'`, `originalAcceptanceSha256`, the pinned DEVEE `origin`, `orgId`, `username`, `isSandbox:true`, reviewed `apiVersion`, exact `userId` and `profileId`, and exactly five `observations`. Each observation contains `input` (one of the five relevant fingerprint names), `originalInputSha256`, `files`, `reads`, and `expectedSha256`. Files specify `{root:'candidate'|'controller'|'setup',path,sha256}`; the optional setup root is `FCOS_HOSTED_DEPENDENCY_SETUP_DIRECTORY`. Reads specify either `{kind:'describe',object,tooling:false}` or `{kind:'query',object,tooling,fields:['Id',...],limit,where?:{field,values}}`. Identifiers and literal values are bounded and validated; no caller supplies raw SOQL, URLs or executable code. Queries use generated SELECT, optional IN equality, ORDER BY Id and a maximum 2,000 rows. Incomplete pagination fails.

The observation digest is the canonical JSON SHA256 of `{files:[{root,path,sha256}],reads:[{recipe:<read specification>,sha256:<canonical complete response digest>}]}` in recipe order. The setup review establishes that these comparable digests correspond to the original relevant application, harness, Salesforce source, synthetic fixture and environment assumptions. The collector first GET-verifies the actual DEVEE sandbox and approved active user/profile, then hashes real files and GET-reads the approved metadata. It maps back to original fingerprints only after every comparable digest matches. The dedicated `FCOS_HOSTED_SALESFORCE_READ_TOKEN` is a one-time scoped credential setup input; values and raw Salesforce records never enter the report. Missing files/recipe/credential remain `waiting_dependency`; mismatched source, identity or readback fails.

For historical NomB publication, the publisher reloads pinned originals and recipe, checks the producer's measured digests and timestamp against the actual successful job, and independently reruns the immutable importer. Only that exact deterministic `nom_b` proof may use the common publisher's `validateHistoricalCheck` seam to retain its original completion time. Ordinary or volatile checks still require capture during their actual producer job. Current financial preservation remains volatile, and its snapshot digest is independently recomputed from the admitted exact table/key baseline.

Hosted session admission also binds `manifest.setupSha256` to the reviewed repository setup and its independent pinned SHA, including dependency file hashes, verification inputs, epoch, controller and targets. `setup.dependencyArtifact:{runId,name}` identifies the immutable Actions setup artifact downloaded by the root workflow. With `FCOS_HOSTED_DEPENDENCY_SETUP_DIRECTORY=dependency-setup`, default filenames are `handoff.json`, `artifacts.json`, `recipe.json`, and `membership.json`; explicit file environment variables override these names. Additional non-executable recipe files remain inside that directory and are individually hash checked before comparison.

When the legacy deployed Salesforce tree fingerprint and the controller's canonical path/hash-pair digest use different formats, the admitted handoff must contain exactly `sourceMapping:{candidateSalesforceSourceSha256,originalSalesforceSourceSha256,measurementRecipeSha256}`. These bind the current manifest digest, original relevant fingerprint, and the same pinned recipe. Missing, mismatched or unreviewed mapping fails. The GET-only recipe must still match every original comparable observation; it returns the original fingerprint, never substitutes the new digest for a measurement. Reports distinguish current `salesforceSourceSha256` and `originalSalesforceSourceSha256`, preserve the original evidence time, and include the mapping digest. Same-format evidence can retain direct equality without a mapping.
