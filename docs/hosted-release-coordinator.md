# Durable hosted release coordination

The coordinator stores serialization and immutable evidence in the pinned Supabase project's private `fcos_release_coordination` schema. It grants no provider or financial authority. One durable operation owns the global lock across release and financial adapters. Each database request is one short transaction; the provider call happens after `begin` commits and outside that transaction. A confirmed outcome releases the lock. Timestamps, runner exits, duplicate dispatch, and a new epoch never expire or steal it.

## Host and credentials

Run the Node 24 entrypoint `supabase/functions/release-coordinator/server.mjs` in a **separate isolated service**, using the supplied Dockerfile with repository-root build context. The Request handler in `index.ts` is also the tested Deno-compatible entrypoint, but **ordinary hosted Supabase Edge Functions cannot satisfy this isolation boundary**: Supabase automatically injects database/admin keys. Its startup guard deliberately refuses that environment. Do not put the service in the FCOS app's provider-secret environment. See [Supabase default secrets](https://supabase.com/docs/guides/functions/secrets#default-secrets).

Configure only:

- `FCOS_COORDINATOR_DATABASE_URL`: direct `postgresql://fcos_coordinator_runtime:<private-value>@db.<pinned-project-ref>.supabase.co:5432/postgres?sslmode=verify-full`, or IPv4 session pooling with username `fcos_coordinator_runtime.<pinned-project-ref>` and the exact `Session pooler host` in `config/fcosConnections.js`, also port `5432`. That hostname was observed in the pinned project's Connect dialog; it is not inferred from its region. The selected Vercel host passed container isolation but could not route to the direct IPv6 address. The guard rejects transaction-pooler port `6543`, arbitrary pooler hosts, duplicate/query override parameters and weak TLS. Both entrypoints construct explicit driver options with hostname and CA verification, then require the actual login and current role to be `fcos_coordinator_runtime` in database `postgres`. The migration creates this role `NOLOGIN`; a separate authorized provisioning step sets its login/password securely. Never grant it role memberships, public table access, or external SECURITY DEFINER execution. See [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres).
- `FCOS_COORDINATOR_GITHUB_METADATA_TOKEN`: a dedicated fine-grained read-only token belonging to the canonical operator, restricted to the pinned repository, with Actions, Contents, Administration/protection and mandatory Metadata reads. Branch reads require Contents; environment/review-history reads require Actions, so no separate Environments permission is needed. The endpoint first verifies `/user`, then uses fixed repository GET routes. Fine-grained token permission provisioning must be independently verified; repository user permissions alone do not prove a token is read-only.
- `FCOS_COORDINATOR_POLICY`: public immutable admission configuration. Pin repository and numeric repository ID, `ref: "refs/heads/main"`, `registrationJob: "release / prepare"`, `approvalJobPrefix: "release / production / "`, `resumeJobPrefix: "release / execute / "`, and `workflows: [{callerWorkflowRef, jobWorkflowRef, jobWorkflowSha}]`. Caller ref must be the pinned repository's default-branch wrapper; reusable workflow ref must end in `@<exact 40-character SHA>` matching `jobWorkflowSha`. Also supported are the direct `prepare`/`register` job names with the corresponding `production / ` prefix. No caller-provided workflow names are trusted.
- Optional `FCOS_FINANCIAL_COORDINATOR_POLICY`: a separate HTTPS issuer/JWKS and audience `fcos-financial-coordination`, with an explicit existing owner allowlist. JWTs must use ES256/EdDSA, bind `owner_id` and `sub: fcos-financial:<owner>`, expire within five minutes, and declare `coordination_only: true, provider_authority: false`. This adapter does not replace financial approval, locks, evidence fingerprints, settlement checks, quotas, or uncertain-outcome readback.

For [pre-merge qualification](hosted-release-bootstrap.md) only, the policy may additionally contain `qualificationAdmission: {repository,repositoryId,ref,bootstrapSha,callerWorkflowRef,callerWorkflowSha,jobWorkflowRef,jobWorkflowSha,candidateSha,setupSha256}`. `callerWorkflowSha` equals `bootstrapSha`; the caller is the exact registered `authenticated-release.yml` path on the separately protected qualification ref. The reusable controller ref ends in its exact `jobWorkflowSha`. This separate administrator-reviewed tuple never replaces the main policy. OIDC and fresh GitHub branch/protection/run/operator metadata derive `qualificationOnly` on the server; client-supplied principal fields are forbidden. The manifest must carry matching `{ref,bootstrapSha,callerWorkflowRef,controllerSha,candidateSha}` in `qualificationSource`, plus the exact setup hash. SQL enforces qualification stage/mode, the single qualification epoch and only Preview/simulation phases. Production approval/resume, financial access, release-mode registration and any use after activation are rejected independently of client checks.

No Vercel, Salesforce, Xero, Google, application service-role, signing-private-key, or other provider secret belongs in this service. Startup rejects broad secret variables, wrong database target, broad database roles, inherited role memberships, application-table access, and executable external SECURITY DEFINER functions. The service exposes no credential values in errors. Terminate HTTPS at the isolated host's ingress and disable request body/header logging.

The database-only TLS trust anchor is `supabase-root-2021.crt`, downloaded from the pinned project's **Database Settings → SSL configuration → Download certificate** link: `https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt`. Its certificate SHA-256 fingerprint is `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA`, expiring 26 April 2031. Both hostname verification and `rejectUnauthorized:true` remain mandatory. This public certificate changes neither system-wide trust nor HTTPS trust for GitHub/JWKS. A provider CA rotation requires an affected source review and actual TLS verification, never a fallback to insecure TLS.

## HTTP and client contract

POST JSON `{action, payload}` with the current identity JWT as Bearer token. GitHub audience is `fcos-release-coordinator`. Signature/JWKS, issuer, audience, repository ID/name, default ref, exact reusable workflow ref/SHA, caller workflow ref, hosted runner, dispatch event, first run attempt, and token/run identity are required. Financial callers also send `x-fcos-coordination-adapter: financial`.

`createCoordinatorClient({url, tokenProvider, fetch, epoch, owner})` exposes `request(action,payload)` and `snapshot`, `register`, `claim`, `begin`, `approve`, `resume`, `complete`, `uncertain`, `readback`, `appendEvidence`, `finish`. Owner is `{kind: "release", id: "features"}` or the exact signed financial owner. Every request binds epoch, owner, release ID and manifest hash. The manifest is stored unchanged and its canonical SHA-256 is recomputed at the endpoint. Its `scope` remains the business scope object; `executionMode` is `qualification`, `release`, or `financial`.

- `register({releaseId,manifest,manifestHash})` is idempotent only for identical immutable contents. It records the first registration immutably and appends a separate prepare admission for each new workflow-dispatch run/attempt before the protected job. Unrelated newer `main` commits do not change the admitted reusable controller SHA or the original manifest. Registration in the Production environment is forbidden.
- `begin({releaseId,manifestHash,phase,operationId,requestHash})`/`claim` returns `execute` exactly once, `readback` for an existing unresolved intent, `complete` with saved evidence for a consumed terminal operation, or `busy` for another unresolved operation/import. Phase is one of `preview.create`, `production.stage`, `production.promote`, `production.rollback`, or `financial.*` for the financial adapter. The additional `qualification.stage`, `qualification.promote`, and `qualification.rollback` phases are coordinator-only simulations, allowed only for qualification manifests outside Production/resume environments and never with provider mutation credentials. Operation ID and phase cannot be rebound.
- `complete` and `readback` take `{phase,operationId,evidence}`. Definitive evidence has `outcome: "applied" | "not_applied"` and provider readback in `result`. Unknown readback retains the lock. An absent/not-applied result still consumes the original intent; it never grants another submission.
- `uncertain` accepts an evidence object or a reason; it only appends uncertainty.
- `appendEvidence({key,evidence,evidenceId?})` appends immutable history. The client derives a stable ID from the bound evidence when omitted; it never adds a timestamp. A changed volatile observation gets a distinct append-only record. Snapshot `checks` selects the latest evidence per key without rewriting older evidence.
- `approve` independently validates the actual GitHub run, non-bypassable Production environment, configured single operator, protected default branch and trusted required checks, exact prepare and manifest-hash-bearing protected job names, and one unambiguous environment review. It stores a server-side receipt for the immutable manifest. Expiry is exactly 24 hours after the first durable protected-job admission, including a failed or interrupted first metadata validation. Repeated validation does not refresh it. Production begin additionally requires the Production environment identity and an unexpired receipt covering that phase. Qualification can never gain Production authority. The client returns `manifestHash` and `expiresAt` as well as the full receipt.
- `resume` is used by the executor after the separate initial approval-only gate job succeeds, including another job in the same run. It is accepted only from the separately protected `fcos-hosted-production-resume` environment, which has no routine reviewer. It requires an existing unexpired immutable approval, a separate prepare admission for the new dispatch, current protected refs and the exact admitted reusable controller, and verified actual job/environment metadata. It appends a resume admission while preserving the first receipt and its original expiry. That environment cannot call `approve` or create/refresh authority. After expiry, a distinct run with a new actual Production review may append a new authorization session for the same immutable manifest. The protected job must start after the prior session expired. Every prior receipt/expiry remains unchanged; resume admissions bind the latest session ID and cannot revive older authority. Original consumed intents still permit only saved completion or GET-only readback.
- `snapshot` returns mode, operations keyed by phase, latest checks, full evidence history, latest immutable approval plus append-only `approvalHistory`, global lock ID, and terminal status. `finish({status})` is allowed only with no unresolved operation for that release. It does not release another owner's operation.

An unknown HTTP outcome is never retried automatically. On a lost begin response, read the journal and perform provider GET-only discovery for the original operation. Neither a new runner nor a new run attempt grants another write.

Qualification source metadata is refreshed only for `register`, `begin` and `claim`; journal-only actions still authenticate signed identity and the exact admitted manifest/epoch but make no new GitHub metadata reads. Approval and resume collect their own required live metadata. A shared per-service-process scheduler limits these collectors to two concurrent reads and 45 reserved reads per rolling minute. Reservations cover queued/in-flight work and remain charged for 60 seconds after completion. This is not a repository-wide or multi-instance quota guarantee: measure aggregate provider traffic during hosted qualification, and retain the financial owner's independent quota controls.

When the complete collector budget is unavailable, the endpoint returns HTTP 429 with exactly `{"error":"COORDINATION_METADATA_PENDING"}` and `Retry-After: 1..60` **before any storage request**. The release client may wait at most three minutes and repeat only that definitive response, preserving the exact request bytes, operation ID and evidence timestamps while obtaining a fresh identity token. A timeout, lost response, malformed response or any other error remains uncertain and is never automatically retried. Exhausting the bounded wait reports the pending phase and resumes from the unchanged manifest/journal; it grants no provider submission.

## Privileged cutover and qualification

These SQL functions are available only to the database migration operator; the endpoint role cannot call them. No function automatically deploys, fences a legacy writer, activates a service, or clears a provider outcome.

1. Inventory **every** legacy release and financial writer and every possibly submitted operation. Save the exact legacy coordinator snapshot and its SHA-256, source hashes, owner IDs and unresolved intent evidence. Pause/fence every old writer using the root cutover helper's permanent durable sentinel, then verify the actual sentinel and all writer shutdowns. Do not rely on a PID, local memory or elapsed time.
2. Call `install_epoch(nextEpoch, inventory)` only with verified `inventoryComplete: true`, `inventoryHash`, `legacyFence: {kind: "permanent_legacy_sentinel", snapshotHash, proofHash}`, `writers: [{id,disabled:true,proofHash}]`, and `uncertainties: [{operationId,evidenceHash,...}]`, and `notificationChallenge:{challenge,issuedAt,repository,operator}` generated once from the canonical setup helper. It installs the same global row in **qualification** mode. A missing sentinel/inventory/fencing proof is rejected; the initial service is frozen. This privileged attestation must be constructed from actual saved evidence, never release-caller JSON.
3. Imported unknown operations block **all** new consequential operations. Reconcile each using original provider GET-only discovery. Only the operator may call `resolve_import(operationId,{outcome:"applied"|"not_applied",evidenceHash,...})` after definitive readback. Unknown cannot be cleared. Reinstallation refuses unresolved imports or an open current operation.
4. Run an actual hosted qualification manifest (`executionMode: "qualification"`) through the same endpoint and global row. Only actual Preview creation and the three explicit coordinator-only simulation phases are allowed while in qualification mode; legacy writers remain permanently fenced. Complete the exact Preview intent after definitive provider readback, exercise lost-response/crash recovery for all three simulated boundaries with `result.simulated: true`, then append the verified hosted proof with `key: "hosted.qualification", status: "passed"`. Record its canonical evidence hash and immutable artifact/source/deployment identities. A fake/simulated result must not be used as an activation proof.
5. Privileged `activate(epoch, proof)` requires the current qualification epoch, no open lock/import, a matching completed actual Preview operation, all three completed simulation intents, its append-only passing qualification evidence, exact `oldWriterFenceHash`, `allWritersAdmitted:true`, and `writerAdmissions:[{id,admitted:true,proofHash}]` for every inventoried writer. Its `manifestHash` and `evidenceHash` must match the stored records. It additionally requires `notificationDelivery:{receiptJson,receiptSha256}` from the actual direct-human confirmation of setup delivery to the canonical operator's iPhone, bound to the immutable installed challenge. SQL recomputes the exact UTF-8 receipt hash and validates the nonce, repository/operator, device, strict boolean confirmation and original receipt time. The administrator must independently review the authentic human reply source; a hash proves integrity, not provenance. Normal release evidence and runtime credentials cannot install this receipt. See the [one-time setup receipt procedure](hosted-release-cutover.md#one-time-iphone-delivery-prerequisite). The operator independently verifies actual hosted qualification and that each new writer uses the shared adapter. It records the proof and notification receipt immutably and changes the same global row to active only when every prerequisite exists. It never removes the legacy sentinel.
6. Only now may ordinary release and financial owners use the active epoch. Production still requires actual GitHub approval of its exact immutable manifest. A changed scope requires a new manifest and approval. Keep old writer fencing after rollback; application rollback must never drop/reset this schema or its journal.

Admin attestation records evidence; it cannot by itself prove an external writer is stopped. The root cutover verifier must compare actual sentinel/snapshot/writer/source hashes before invoking these RPCs. The database operator remains a trusted administrative boundary.

## Verification

Run `node --test tests/hosted-release-coordinator*.test.js`. Set `FCOS_REQUIRE_NATIVE_COORDINATOR_DATABASE=1` in the required coordinator database gate to fail when native PostgreSQL is unavailable. PGlite applies the actual migration and exercises the real Request entrypoint with signed tokens. When PostgreSQL's `pg_config`/server binaries are installed, the native test starts its own Unix-socket-only temporary cluster and races independent sessions. It cleans up that cluster, proves one execute for 24 concurrent begins, durable crash/unknown locks, adapter contention, private grants, and endpoint RPC operation with the minimal role. No live project access is used.

`scripts/verify-migrations.mjs` drops the private schema only in its existing disposable-local-database reset path; its localhost guard remains mandatory. This is test cleanup, never a rollback strategy. Do not expose the private schema through PostgREST or grant browser/service-role access. Security-definer dispatch is deliberately private and owned by a NOLOGIN role restricted to this schema, with fixed search paths, parameterized values, explicit grants, RLS, and append-only triggers.

## Executable qualification and local rehearsal

`runQualification({manifest,coordinator,simulateProduction:true,context:"hosted",repositoryId})` in `scripts/hosted-release-qualification.mjs` requires the real completed Preview intent, matching stored READY deployment, a bound `preview_binding` proof, and every required accepted check. Missing evidence returns `waiting_dependency`; it never supplies synthetic NomB, preservation, financial-owner or business proofs. Hosted execution verifies current GitHub OIDC against the admitted reusable controller and rejects Production/resume environments and provider mutation credentials. Only its fixed coordinator-only stage/promote/rollback simulator is used. Simulated effects are appended before completion and are recovered by GET-only journal readback after a lost response.

The flow writes `qualification.pending_artifact`, then the qualification job uploads `qualification.json` as `fcos-<releaseId>-qualification`. A separate publisher invokes `publishQualificationArtifact({manifest,coordinator,github,runId})`, using the verified `github.read/pages` client. Its defaults select job `release / qualify`, the exact artifact name and file above. It independently checks actual GitHub run/job/reusable-controller identity, successful `Run admitted checks` producer step, immutable archive digest, original report/artifact/job timestamps, stored Preview identity, all three simulation outcomes, and the exact original accepted check records. Only then does it append `hosted.qualification` with `actualGithubArtifactValidated:true`; SQL activation requires this marker and the exact evidence hash. The privileged operator still independently verifies the actual hosted run/artifact and writer-fencing evidence before activation.

`context:"local_rehearsal"` writes only `local.qualification`. It cannot satisfy activation. `FCOS_REQUIRE_NATIVE_COORDINATOR_DATABASE=1 node --test tests/hosted-release-qualification.test.js` runs a disposable native PostgreSQL rehearsal with signed local OIDC keys, the real endpoint/client/controller/publisher, and fake Vercel/GitHub boundaries. It covers pending evidence, a delayed gate and moved main, a lost committed simulation response, new-run readback of an uncertain staged write, same original authorization expiry, promotion, lost-response rollback, and explicit later human-review renewal preserving the expired session and original staged POST. Native activation also requires a synthetic local setup receipt; that fixture is never actual human delivery evidence. These results are local integration evidence and never hosted qualification or business authority.
