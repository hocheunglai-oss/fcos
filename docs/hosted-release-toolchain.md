# One-time hosted toolchain publication

`hosted-release-toolchain.yml` publishes the reviewed verification image with GitHub's short-lived `GITHUB_TOKEN`. It does not require expanding the Mac's personal token permissions. The workflow is disabled by default and cannot deploy FCOS, access provider credentials, admit its own output or activate coordination.

Before dispatch, the setup operator verifies the pinned GitHub identity and repository, acquires the **existing canonical provider-write lease**, and records a durable intent for one registry publication from the exact reviewed source. Set `FCOS_HOSTED_TOOLCHAIN_SOURCE_SHA` to that immutable source and `FCOS_HOSTED_TOOLCHAIN_INTENT_SHA256` to the intent digest, then enable `FCOS_HOSTED_TOOLCHAIN_SETUP_ENABLED`. These setup writes and the dispatch are covered by that same held lease and exact scope. Do not release the lease merely because GitHub accepted dispatch.

Dispatch only through the separately protected qualification bootstrap as the pinned repository owner with the exact admitted source and intent. The publisher exposes `workflow_call` only; there is no independent main/direct-dispatch path. Every publication therefore shares the registered `authenticated-release.yml` history and cannot replay one intent through another workflow namespace. Only first attempts are admitted. Before publishing, a target-locked GET-only guard verifies the complete workflow history and requires every earlier run number to be present. Any earlier run with the same intent consumes it, regardless of success, failure or uncertainty. The global workflow concurrency guard serializes these reads and publication. Never delete or rewrite this setup workflow's run history; a gap fails closed. The build job has read-only source access and no registry/provider secret. It builds Linux AMD64, verifies the non-root image user and records actual runtime versions. The separate publisher loads the byte-checked artifact without executing it, verifies the admitted guard's bytes, obtains registry write access only for its one push, reads the immutable registry digest, and removes its temporary Docker login.

Use the [protected qualification bootstrap](hosted-release-bootstrap.md) before the consolidation PR merges, with `bootstrap_phase: toolchain`. It calls this workflow by immutable SHA through `workflow_call`. In addition to the source/intent pins above, install public `FCOS_HOSTED_TOOLCHAIN_BOOTSTRAP` JSON containing `{schemaVersion:1,repository,repositoryId,ref,bootstrapSha,controllerSha,callerWorkflowRef}` and `FCOS_HOSTED_TOOLCHAIN_BOOTSTRAP_SHA256`, the SHA-256 of the exact UTF-8 JSON bytes. The branch name must start `codex/hosted-qualification-`. The caller is the existing registered `authenticated-release.yml` path on that exact protected ref; its commit and the referenced reusable toolchain SHA are independently checked before publication. The pre-build context check rejects unadmitted branches before executing the Dockerfile. Publication also verifies the current live branch SHA/protection and actual run identity, and scans the complete history of the registered caller workflow for prior intent consumption. A missing/deleted history entry blocks publication; do not reset history to work around it.

This bootstrap uses only GitHub's short-lived built-in registry token. It adds no personal-token permission or provider credential. Keep the existing canonical write lease held across setup, dispatch, image publication and definitive registry readback. Disable its setup flag and include both the registered caller and reusable publisher in the writer-fencing inventory before installing the qualification epoch.

After the run, independently verify the actual protected run, source, successful build and publication jobs, artifact digests, registry digest and source label. Retain the image by digest in the reviewed setup. Publication alone is **not** hosted qualification or image admission. Resolve the old lease only from that actual readback and root acceptance.

A failed or lost push response is uncertain. Preserve the original publication intent, use registry GET-only readback for its exact tag, and never rerun a consumed invocation or infer that an absent listing proves no write. The tag includes source and run ID; it is not used as the release runtime reference.

Disable this one-time workflow after publication. Include it in the complete old-writer inventory and permanent fencing before the new coordinator epoch is installed. The setup enable flag is not routine release authority; an active epoch must not coexist with this independently coordinated publisher. Routine releases reuse the qualified immutable image and do not rebuild or republish it.

## Finite repair while epoch 1 remains inactive

If the installed qualification epoch needs a replacement verification image, keep the legacy `FCOS_HOSTED_TOOLCHAIN_SETUP_ENABLED` flag exactly `false`. Use the distinct `FCOS_HOSTED_TOOLCHAIN_EPOCH_PUBLICATION_ENABLED` flag only under a reviewed finite administrator operation in that same existing coordinator. This path is unavailable after activation or qualification admission. It does not create a second coordinator, change the old fencing records, grant Production authority, or add a database credential to GitHub.

The original operator verifies the actual inactive epoch and administrator admission, obtains its genuine canonical lease using the accepted guarded-provider-write helper, and retains that lock across the protected dispatch, build, single registry push and definitive owner readback. Record each setup/arming/dispatch/disarming provider write in the admitted finite operation; do not hide several writes behind one provider callback. The build has no registry credential. Its elapsed time does not expire the administrator lock. A dispatch acknowledgement alone must not record the final submitted outcome or release that lock. Unknown dispatch or push outcomes stop later writes and permit only exact original-owner readback, with no replay or lease takeover.

Install `FCOS_HOSTED_TOOLCHAIN_EPOCH_PUBLICATION` and `_SHA256` (SHA-256 of exact UTF-8 JSON bytes). The JSON has exactly these fields: `{kind:"fcos_hosted_toolchain_epoch_publication_v1",schemaVersion:1,epoch:1,mode:"qualification",activated:false,qualificationAdmitted:false,sourceSha,intentSha256,bootstrapSha,callerWorkflowRef,rootReviewSha256,scopeSha256,lease}`. Source, intent and caller match the existing immutable bootstrap inputs. The lease has exactly the existing nine fields `{epoch,objective,ownerThreadId,operationId,bindingSha256,leaseId,coordinationOnly:true,providerAuthorityGranted:false,uncertainOutcomeRequiresReadback:true}`. Preserve the existing administrator's labels `epoch:"fcos-hosted-admin-epoch1"`, `objective:"production"`, and `ownerThreadId:"01a0f08b-7fcb-7870-9edc-343e16052b62"`; the historical objective label grants no Production authority. The operation, binding and UUID must be the actual held lease. These public bytes are context checks, not evidence that a lease exists; the independent operator must assert the real database lease at the required boundaries.

Both pre-build admission and the publisher guard require this binding and reject missing hashes, changed source/caller, unknown fields, active/qualified flags, the legacy enable flag, or a changed lease shape. The existing first-attempt and complete caller-history checks still consume the intent across both modes. No additional GitHub environment reviewer is declared by the toolchain jobs; an actual platform-enforced review remains authoritative if present.

After the known terminal run, independently verify build/publication jobs, immutable artifact/archive hashes, registry digest and source label, and assert the original database lease. Disable the epoch publication flag and verify it while that same finite scope remains held. Only after definitive registry and disarming readback may the original operator record completion/release. Retain the new digest and actual version records in a newly reviewed setup; this is not hosted qualification or activation. Candidate bootstrap rejects PostgreSQL outside 16/17 before dependency installation. The maintained image explicitly installs PostgreSQL 17 and proves a disposable non-root database with `pgcrypto` before it is saved for publication.
