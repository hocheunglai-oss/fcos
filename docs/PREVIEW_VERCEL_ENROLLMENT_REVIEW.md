# Project-scoped Preview token authority review

This default-off path addresses the observed project PAT limitation: the same protected `vcp_` bearer can read the exact FCOS project while both `/v5/user/tokens/current` and the reviewed-ID metadata endpoint return 404. Reading another token's metadata with a management credential does not identify the runtime bearer. The legacy current-token authority module is unchanged; there is no fallback from its failure.

## Trust and scope

A new project PAT must be created once, under separate exact owner authorization. The single issuance response pairs its one-time bearer with its token ID. A fresh management-plane read of that exact ID must independently prove the FCOS project, sole pinned team, unrevoked/unleaked state, and exact expiry of at most 24 hours. The operator retains the management credential locally through the existing approved connection. CI receives only the issued project PAT and its private enrollment companion.

The companion commits to the enrollment fields with HMAC-SHA256 keyed by the issued bearer. A per-run Ed25519 receipt signs the canonical public metadata and that private binding under the hard binary domain `FCOS-PREVIEW-VERCEL-RUN-AUTHORITY-V1` plus NUL. Its signature cannot be reused as the existing JSON connection-health attestation. The existing pinned Keychain attestor is reused only with explicit authorization for this new purpose; no key is generated or silently replaced. The private HMAC tag never appears in public receipts, diagnostics or artifacts.

Each receipt binds repository and environment IDs, enrollment/token identity, protected harness commit, control revision, contract, candidate, workflow run ID, first attempt and operation. Its maximum age is ten minutes and it never outlives the PAT. Metadata observation is recorded immediately after the response, after any Keychain consent delay. Publication consumes this lifetime. Changing the PAT, companion, receipt, source, operation, run or attempt fails closed. Freshness is checked after scope reads, after retained Production, at the final authority return and immediately before the deployment POST.

## Default-off controls and verification

`FCOS_PREVIEW_VERCEL_AUTHORITY_MODE=issuance-bound-v1` and `FCOS_PREVIEW_VERCEL_ISSUANCE_AUTHORITY_ENABLED=true` are separate protected environment controls. `FCOS_PREVIEW_VERCEL_ENROLLMENT_ID` selects the exact enrollment. `FCOS_RELEASE_VERCEL_ENROLLMENT` is a protected secret; `FCOS_PREVIEW_VERCEL_AUTHORITY_RECEIPT` contains only the public signed envelope. Absent mode remains `legacy-current-v1`.

The first approved use is the separate `verify-authority` operation. Repository admission and fresh environment checks require Preview and Production deployment gates false and the diagnostic flag true. Existing owner review, protected main, OIDC and source/configuration checks remain mandatory. The runner performs exactly four fixed scoped GETs and the retained Production GET, then returns before environment-record reads, intent, execution claim or deployment. Its sanitized artifact reports `authorityVerified=true` only if every scope and Production check succeeds. A partial/malformed project list or changed Production fails the workflow after recording false evidence. A later create/readback receipt must bind that different operation; verification does not enable builds.

The unfiltered fixed `/v9/projects?limit=100` first page must contain exactly one matching FCOS row, exact count and `next:null`, with no true `hasMore`. A positive numeric/timestamp `prev` is allowed only in this new mode: the provider's pinned 54.20.1 client itself decides first-page completeness from `pagination.next`. Bare arrays, missing `next`, filtered paths, incomplete counts and other projects fail. User 404/not_found is accepted only together with signed exclusive-project scope and runtime binding; team access must still return 403. Exact repository, disabled automatic Production, domain assignment and empty hooks remain checked.

## Local operator helper

`node scripts/preview-vercel-enrollment.mjs --plan` makes no provider or Keychain calls. Execution accepts only `--execute-approved enroll|attest <approval-uuid>`. It reads the private file `.fcos-cli/preview-vercel-enrollment/approval-<uuid>.json` under the verified shared primary checkout. No credential path, provider target, public key, gate activation, dispatch or deployment override is accepted by the CLI.

An approval has `schemaVersion:1`, exact `action`, `authorized:true`, canonical `authorizedBy`, truthful `authorizationEvidence`, millisecond `authorizedAt` within one hour, `nonce`, `enrollmentId`, exact `target` from the plan, `scriptSha256`, `harnessSha`, `candidateSha`, `controlRevision`, `contractSha256`, `expiresAt`, and `leaseDeadline`. Enrollment also requires the unchanged `previousReviewedTokenId` and exact full existing `secretMetadata` entries `{name,created_at,updated_at}`. The allowed baseline names are `FCOS_E2E_VERCEL_BYPASS`, `FCOS_RELEASE_GH_TOKEN`, `FCOS_RELEASE_PREVIEW_RUNTIME_TOKEN`, `FCOS_RELEASE_RUNTIME_TOKEN`, and `FCOS_RELEASE_VERCEL_TOKEN`, plus an optional existing `FCOS_RELEASE_VERCEL_ENROLLMENT`; GH and PAT metadata are mandatory. Attestation additionally requires `attestorNewPurposeAuthorized:true`, `runId`, and `operation` (`verify-authority`, `create`, or `readback`). This local approval file authorizes operator actions only; it is never accepted by CI as authority evidence.

The helper verifies the Git remote, clean exact installed source, owner identities, protected main/environment, pins, competing release/proof runs, project configuration and exact retained Production. Local management GETs use the pinned capable CLI with one captured management token. CLI 54.20.1 `tokens add` cannot specify exact expiry, so issuance uses one fixed HTTPS POST with `projectId` and `expiresAt`. It does not retry. Raw responses, bearer, companion and private key remain in memory; child command output is buffered and arbitrary errors are suppressed without property inspection.

Enrollment writes a durable exclusive intent before issuance. The private companion is held in the fixed enrollment Keychain service under the approved enrollment UUID account. The reviewed Swift helper gains only bounded `set-stdin`; no private temporary file or argument is used. It is compiled from exact tracked source into a fresh owned directory. Paired GitHub secrets are written with buffered stdin, with the exact owner rechecked before each mutation. Only after both writes and metadata readback does the helper repin token/enrollment IDs. Every non-target secret must retain its exact metadata, with no additions or removals; the complete resulting snapshot is rechecked before attestation. All enable flags remain off. Private files reject symlinks, hardlinks and non-private modes; state replacement is atomic and flushed.

Any uncertain issuance, failed metadata proof or partial secret write is quarantined. Its existing exclusive intent prevents another POST. Do not rerun issuance with another nonce/enrollment to work around this: first reconcile the exact token name `fcos-preview-enrollment-<enrollment UUID>` through an approved management metadata read. A lost one-time bearer cannot be recovered. Revocation of a confirmed orphan or another issuance requires its own exact owner authorization. Attestation also claims its approval nonce before signing/publication, so uncertain publication is read back before a separately approved refresh.

## Required approval and remaining live evidence

Code/tests do not authorize token creation, credential replacement, Keychain writes, signing, environment activation, installation or dispatch. The exact issuance expiry must respect the currently approved lease; this change grants no extension. An expired prior lease requires a separately approved replacement lease.

Before execution, review/freeze the helper and installed source hashes, exact new PAT scope/expiry and old/new secret targets, enrollment UUID, attestor purpose, metadata baseline and allowed per-run receipt publication. Activation and the human-reviewed `verify-authority` dispatch remain separate operations. The helper does not perform them. Success requires the live archive to prove actual same-runtime binding, complete one-project list and retained Production; fixture success alone does not resolve the provider issue.

Unverified live assumptions are the documented paired issuance response and metadata shape, the actual project-list pagination shape, CLI behavior under the new installed worktree, and end-to-end paired-secret/Keychain storage. Offline tests use public RFC8032 fixture keys, fake providers and a Swift stdin-only harness with no Keychain symbols. No operational key, token or provider write is used by these checks.
