# Qualification before the consolidation PR merges

The temporary bootstrap lets the actual hosted controller qualify while all repairs remain on one draft PR. It is a one-time setup path, never a second Production release path. The normal caller and Production coordinator admission remain restricted to protected `main`.

## Immutable source binding

1. Review and publish the complete controller commit `C` on the consolidation PR. Do not merge it yet.
2. Render `.github/qualification/hosted-release-bootstrap.yml`, replacing all five `__FCOS_CONTROLLER_SHA__` occurrences with `C`. Put only that reviewed rendered file at `.github/workflows/authenticated-release.yml` on a dedicated `codex/hosted-qualification-…` branch based on `C`. Commit this bootstrap as `B`. The existing default-branch workflow supplies GitHub's registered dispatch entrypoint; the protected branch supplies the exact caller. Do not overwrite the default-branch file.
3. Before publishing the branch, suppress its automatic Vercel deployments. Apply and verify its exact protected-source restrictions, environment branch admission and operator identity under the existing setup/write controls. The candidate, controller and bootstrap may be different commits; record each explicitly. Neither an ordinary PR branch nor a mutable branch head is trusted controller authority.
4. Admit the public five-field `qualificationSource` in the release setup: `{ref,bootstrapSha,callerWorkflowRef,controllerSha,candidateSha}`. `callerWorkflowRef` is `hocheunglai-oss/fcos/.github/workflows/authenticated-release.yml@<ref>`. Bind the separately reviewed coordinator `qualificationAdmission` to this tuple, numeric repository ID, caller workflow SHA, exact reusable workflow identity and setup hash. Set `FCOS_HOSTED_QUALIFICATION_ADMITTED=true` only for this admitted tuple. These are one-time administrator decisions, not self-admission by the candidate.

The early manifest entrypoint checks the actual protected branch, run, operator, caller and reusable controller before checking out the candidate or exposing provider observation credentials. Its GitHub read-only credential needs repository Contents, Actions and Administration/protection reads; verify that permission during setup. Store only `FCOS_HOSTED_GITHUB_READ_TOKEN` at repository scope so environment-free prepare/publisher jobs can inspect protection. GitHub requires explicit named forwarding even for environment-only secrets: the bootstrap forwards the exact non-Production secret names declared by the reusable controller, while credential values remain solely in the matching protected job environments. Do not use `secrets: inherit` or copy provider credentials to repository/organization scope. Candidate execution receives no secret expression or credential environment. The Production-only executor bypass is not forwarded by the bootstrap; its separate manifest job may use a read-only Production observation bypass in the verification environment. See [GitHub reusable-workflow secret semantics](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#using-inputs-and-secrets-in-a-reusable-workflow). Both manifest stage and execution mode must be `qualification`. The coordinator independently authenticates OIDC and the admitted tuple on every bootstrap request, deriving a qualification-only principal. It refreshes live source metadata at registration and `begin`/`claim` boundaries. Journal-only operations retain the immutable binding without repeating those reads; this permits readback of an original uncertain submission even after branch drift. New admissions still fail on drift. It rejects registration for another candidate/setup, Production approval/resume, Production writes, financial access and bootstrap use after epoch activation.

## Hosted setup and qualification sequence

Before provisioning the observer login, consume the actual `observer-network-preflight` job from the exact reviewed consolidation source. This independent quality job has no protected environment or provider credentials. It resolves only the canonical FCOS direct database host, sends PostgreSQL SSLRequest, verifies TLS with the committed CA and hostname, and closes without authentication or SQL. Its artifact binds the actual source, GitHub run/attempt, runtime, CA and observed address families. A failed phase blocks observer setup; do not replace it with a Mac/pooler result, disable certificate checks or silently change transport. Passing transport admission does not prove a database login, schema equality, preservation or release qualification. The diagnostic stops automatically when hosted readiness is enabled.

Publish the credential-free check image with the bootstrap's `toolchain` phase and the [one-time toolchain contract](hosted-release-toolchain.md), retaining the existing coordination lease through registry readback. The workflow's built-in GitHub token provides registry permission; do not expand a personal token to make this work. Bind the verified image digest into the setup before qualification. Then disable toolchain publication and fence it with all other legacy writers.

Provision the isolated coordinator host, its coordination-only database role, read-only metadata credential and dedicated hosted verification/Preview credentials. Apply the reviewed migration to the pinned database. Keep Production deployment credentials out of the bootstrap environments. Import the original dependency evidence and permanent legacy fences using the [cutover procedure](hosted-release-cutover.md). Install the single epoch in qualification mode only after every old writer is fenced and all unresolved submissions are recorded. Unknown imported outcomes block new writes until definitive readback.

Enroll the Vercel read Integration once using the [original OAuth exchange and admitted fingerprint contract](hosted-release-verification.md#vercel-read-integration-enrollment). Put its bearer only in the verification, restricted and normal protected environment `FCOS_HOSTED_VERCEL_READ_TOKEN` slots. Bind public client/integration/configuration IDs and proof hashes in `verification.vercelReadCredential`, with its root-review bytes at `setup.vercelReadCredentialAcceptance`; these replace the obsolete read-PAT token-ID variable. Its `notAfter` is a local admission horizon, not provider-enforced expiry. The new finite Preview writer PAT remains only in `fcos-hosted-preview`, under `FCOS_HOSTED_VERCEL_TOKEN` and its existing public writer ID. Read enrollment grants no Production or financial authority and requires no routine Mac or human signing window.

The caller explicitly forwards the existing repository `FCOS_E2E_EMAIL`/`FCOS_E2E_PASSWORD` into restricted-only fallback slots. The restricted matrix step selects either a complete dedicated hosted pair or the complete existing pair, never mixed fields. Normal and runtime credentials remain separate. The FCUNO public contract GETs accept no token; `FCOS_HOSTED_FCUNO_READ_TOKEN` is optional and requires no new credential setup.

Dispatch the existing registered workflow on the exact protected bootstrap ref with `bootstrap_phase: qualification`, the admitted candidate and a qualification plan. It runs the real Preview deployment, candidate isolation, deterministic/database/browser checks, immutable publisher and validator, followed by the three journaled simulated Production boundaries. Exercise interruption and lost-response recovery by dispatching the same saved manifest in a new first-attempt run. Do not mint a new manifest or operation to escape an unknown outcome. A repair changes the controller/source admission and remains on the consolidation PR; historical evidence and consumed operations retain their original bindings.

Accept qualification only from actual hosted artifacts and coordinator readback. Verify the operator's actual iPhone notification receipt. Then finish the existing exact-source PR checks and merge the same consolidation PR. Admit the normal main caller, activate the same epoch, and remove only the qualified obsolete intermediate reviewer gates. Disable the temporary qualification flag/branch admission. Production still requires one final protected approval for each immutable deployment manifest.

This sequence neither approves the compatibility release nor combines it with the final application release. The frozen candidate, required Production observation and separately admitted status/supplier scopes remain unchanged.
